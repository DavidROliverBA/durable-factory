What is this?

A hands-on demo of Durable Pi: AI agents whose work survives the process dying. This page runs a real agent server on your Mac. You crash it on purpose and watch what comes back.

The problem it solves

A normal agent keeps its in-flight work in memory: the tool call it's running, the job step it's on, what it's waiting for. Kill the process and that's gone. "Resume" just reloads the chat log, and nobody knows whether the half-finished command ran or not.

A durable agent writes every step to a SQLite database before acting on it: messages, queued input, task checkpoints, waits. When the process restarts, it reads the database and knows exactly where each piece of work stopped.

How this page works

your browser ──► lab server (Bun, :4791) ──► dpi-backend (Node, :4790) ──► agent.sqlite │ supervises the backend process └ 💥 kill -9 · ▶ start · ⚡ crash & restart
  • dpi-backend is the real, unmodified server from the durable-pi repo. It owns the agent, its tools and its database.
  • kill -9 sends SIGKILL: the process dies instantly, with no chance to save or clean up. That's the worst case, like a power cut.
  • The model is a faux (scripted, free, offline) model, so the demo costs nothing and behaves the same every time. The durability machinery is identical with a real model.
  • The browser never talks to the backend directly. When the backend dies, the page shows it reconnecting, then loads a fresh snapshot from SQLite.

Try it

  1. Scenario 1: start the long job, click kill -9 around check 5, then start. The checks carry on from 5, not 1. The red striped band on the timeline is the time the server was dead.
  2. Scenario 2: start the release check and wait for the Approve prompt. Kill the server and leave it dead for a while, then start it. It's still waiting for you. Approve, and it publishes exactly once.
  3. Scenario 3: start the bash loop and kill it mid-way. After restart, the tool is marked INTERRUPTED. The agent is told the command may have partially run, rather than having it silently re-run (imagine that command was "charge the card").

Reading the screen

Header pill
Is the backend process alive? Shows its PID, which changes after every restart, proving it really is a new process.
Durable jobs
Multi-step workflows. Each box is a phase, each dot a checkpoint. resumed ×N means a step was cut off mid-way and re-entered from its checkpoint.
Agent transcript
The conversation, including live tool output.
Live durable tasks
pi-durable's task graph: every model call, tool call and job is a task row in SQLite. These are the rows that get picked up after a crash.
Wire events
The raw event stream. After each reconnect you'll see hello snapshot: nothing is replayed, and the client just reloads the current state from the database.
auto-restart
Simulates a service manager (launchd/systemd) bringing the server straight back.
reset
Wipes all lab data in ~/.dpi-lab and starts fresh.

Scenarios

1Long job, checkpoint by checkpoint

change-watch: baseline the workspace, then 12 checks two seconds apart, one durable checkpoint per check.

→ Crash it at check 5. It resumes at check 5, not 1.

2A human approval that outlives the process

release-check: plan, then a subagent gathers evidence, then the job waits for you before it publishes.

→ While it waits, kill the server and leave it dead. Start it again, then approve. It publishes once.

3A tool call cut off mid-flight

The agent runs a 15-second bash loop. A command that may have partly run is not silently re-run.

→ Kill it around step 6. After restart the result is marked interrupted, and the agent decides what to do next.
